# 틈(TEUM) 구독관리 서비스 PRD 목차 및 내용

---

| 제품명 | 틈(TEUM) |
| --- | --- |
| **제품 슬로건** | 새는 구독비를 잠그다 |
| **한 줄 정의** | 틈은 흩어진 구독·멤버십의 결제, 갱신, 혜택 정보를 한곳에 모아 사용자가 결제 전에 판단하고 행동하도록 돕는 구독 관리 서비스 |
| **핵심 가치** | 현재 구독과 월 예상 비용을 한눈에 파악하고, 결제·갱신·무료체험 종료 전에 행동하며, 
보유 혜택을 실제 사용으로 연결한다. AI가 제안하는 정보는 사용자가 확인한 뒤 확정한다. |
| **핵심 기능** | 내 구독 대시보드, 구독 캘린더, 혜택 점검하기, 결제 내역 이미지 기반 AI 구독 등록, 구독·개인 일정 통합 관리 |

## **1. 배경 및 시장 현황**

구독서비스가 OTT·음원 중심에서 쇼핑 멤버십, 통신 결합상품, 생활가전, 외식·배달 등 생활 전반으로 확대되며, 사용자가 동시에 관리해야 하는 구독 상품 수가 증가하고 있다. 국내 구독경제 시장은 최근 몇 년간 가파르게 성장했다.

## **2. Pain-Point 리서치**

### **2-1. 구독 확대로 인한 관리 대상 증가**

[대한상공회의소·마크로밀 엠브레인 조사](https://www.korcham.net/nCham/Service/Economy/appl/KcciReportDetail.asp?CHAM_CD=B001&SEQ_NO_C010=20120940674)(성인 남녀 1,000명)에 따르면 국내 소비자의 94.8%가 구독서비스 이용 경험이 있으며, 66.1%가 3개 이상의 구독서비스를 이용하고 있다. 자체 설문조사에서도 응답자의 47%가 4개 이상의 구독·멤버십·통신 상품을 이용 중이었다.

### **2-2. 분산된 정보 파악의 어려움**

[Bango 조사](https://bango.com/wp-content/uploads/2024/09/Bango_East_Asia_Consumer_Survey.pdf)에 따르면 한국 구독자의 65%는 모든 구독을 한곳에서 관리하지 못해 불편을 느끼며, 71%는 하나의 앱에서 통합 관리를 원한다. 

자체 설문에서도 68%가 혜택·조건 확인을 위해 여러 앱·웹사이트를 탐색한 경험이 있고, 83%가 이 과정을 번거롭게 평가했다.

### **2-8. 구독료 부담 시 완전 해지를 선택하는 경향**

구독료가 부담되거나 필요성이 낮다고 느꼈을 때, 응답자의 71%가 '완전 해지'를 선택했다. 요금제 변경(11%), 일시정지·결합상품 변경(각 4%) 등 조정 방식을 택한 비율은 낮았다.

### 3-1. 핵심 인사이트 : 문제 발생 흐름

외부 리서치와 자체 설문을 종합하면 사용자의 문제는 단순히 구독 개수가 많다는 데 있지 않다. 여러 서비스에 정보가 분산되어 있어 전체 구독 상태를 확인하려면 여러 앱과 웹사이트를 직접 탐색해야 하며, 결제일·갱신일·혜택 정보도 별도로 기억하거나 기록해야 한다.

## 5. **가설수립 및 우선순위 (ICE)**

### 5-1. 핵심 가설

<aside>

 **가설 1) 내 구독 대시보드**

분산된 구독·결제·갱신 정보를 메인 홈의 내 구독 대시보드에서 한눈에 제공하면 사용자의 구독 현황과 지출 파악 시간이 줄고 구독 관리 화면 진입이 증가할 것이다.

- 근거
    
    <aside>
    
    **Impact** 
    
    다중 구독자의 정보 분산과 관리 부담이 높아, 통합 대시보드가 정보 탐색 부담과 불필요한 지출 발견에 직접적인 영향을 줄 수 있다. 
    **(3개 이상 구독 66.1%, 여러 앱 탐색 68%, 탐색 번거로움 83%)**
    
    </aside>
    
    <aside>
    
    **Confidence**
    
    외부 조사·자체 설문에서 통합 조회 니즈가 반복 확인되어 신뢰도가 높다.
    **(통합관리 희망 71%)** 다만 실제 정보 파악 시간 단축은 프로토타입 테스트가 필요하다.
    
    </aside>
    
</aside>

<aside>

 **가설 2) 구독 캘린더**

결제·갱신·무료체험 종료 정보를 구독 캘린더와 사전 알림으로 제공하면 사용자의 구독 관리 행동이 증가하고 원하지 않는 자동결제가 감소할 것이다.

- 근거
    
    <aside>
    
    **Impact** 
    
    결제·갱신일 누락 경험이 높고 사전 알림 니즈도 확인되어, 캘린더가 원치 않는 자동결제 예방에 영향을 줄 수 있다. **(주요 시점 인지 부족 85%, 누락 경험 80%)**
    
    </aside>
    
    <aside>
    
    **Confidence**
    
    결제 시점 인지 부족과 사전 알림 니즈가 명확히 확인되어 신뢰도가 높다. 
    **(사전 알림 희망 69%, 자동결제 경험 56%)** 
    다만 캘린더가 실제 관리·해지 행동으로 이어지는지는 추가 검증이 필요하다.
    
    </aside>
    
</aside>

<aside>

 **가설 3) 혜택 점검하기**

분산된 혜택 정보를 상태와 제공 서비스 중심으로 정리하면 사용자의 혜택 확인 및 실제 사용 행동이 증가할 것이다.

- 근거
    
    <aside>
    
    **Impact** 
    
    혜택을 놓치거나 인지하지 못하는 사용자가 많아, 혜택 통합 제공이 혜택 미활용과 비용 낭비를 줄이는 데 영향을 줄 수 있다. **(혜택 뒤늦은 인지 82%, 인지 수준 3점 이하 65%)**
    
    </aside>
    
    <aside>
    
    **Confidence**
    
    혜택 인지 부족과 통합 확인 니즈가 확인되어 신뢰도가 높다. 
    **(통합 확인 희망 56%, 사용법을 몰라 미사용 42%)** 
    다만 실제 혜택 사용·비용 절감으로 이어지는지는 추가 검증이 필요하다.
    
    </aside>
    
</aside>

<aside>

**가설 4 ) AI 이미지 등록**

결제 내역 이미지에서 AI가 구독 후보를 찾아 초안을 제공하면 구독 등록 완료율이 높아지고 수동 입력 부담이 감소할 것이다.

- 근거
    
    <aside>
    
    **Impact** 
    
    구독 정보를 직접 입력·관리해야 하는 번거로움이 높아, 이미지 기반 자동 등록을 통해 초기 정보 입력 부담과 관리 이탈을 줄일 수 있다. 
    **(캘린더 미등록 59%, 직접 입력이 귀찮아서 미등록 54.2%, 따로 관리하지 않음 36%)**
    
    </aside>
    
    <aside>
    
    **Confidence**
    
    사용자가 구독 정보를 지속적으로 관리하지 못하는 주요 원인으로 직접 입력의 번거로움이 확인되어, 입력 자동화의 필요성에 대한 신뢰도가 높다. **(직접 입력이 귀찮아서 54.2%)** 
    다만 이미지 인식의 정확도와 자동 등록이 실제 구독 관리의 지속으로 이어지는지는 추가 검증이 필요하다.
    
    </aside>
    
</aside>

- **[ICE 우선순위]**
    
    신규 서비스라 실사용 데이터가 없어 Reach 추정 신뢰도가 낮으므로 **Impact · Confidence · Ease** 기준을 사용한다. 
    
    각 항목은 1~5점으로 평가하며
    
    - **Impact**는 핵심 문제 영향도
    - **Confidence**는 근거 충분도
    - **Ease**는 실행 용이도
    
    를 뜻한다. 
    
    * Confidence는 자체 설문(n=100)과 외부 조사 수치를 근거로 부여

- 가설 기술 Ease 점수 계산에 대한 근거
    
    

### 5-2. 가설 검증 방법

- **내 구독 대시보드** : 사용성 테스트 과업 성공률, 핵심 정보 인지율, 구독 관리 화면 진입률 측정

## 7. 주요 사용자 흐름

### 7-1. 작품 탐색·기록 흐름

**홈 → 내 구독 → 구독 상세 → 정보 수정 또는 종료 기록**

사용자는 홈에서 전체 구독 수와 월 예상 비용, 다음 결제를 확인한 뒤 내 구독 목록으로 이동한다. 특정 구독을 선택하면 요금제, 결제금액, 결제주기, 갱신일, 포함 혜택을 확인하고 필요한 정보를 수정하거나 종료 여부를 기록한다.

**구독 등록 흐름:** 공통 `+` → 구독·멤버십 등록 → 결제 내역으로 자동 등록 또는 서비스에서 선택 또는 직접 입력 → 정보 확인·수정 → 최종 확인 → 등록 완료.

### 7-2. 캘린더 탐색 흐름

**캘린더 → 구독 일정·일상 일정·전체 필터 → 날짜 선택 → 일정 상세 → 연결된 구독 상세 또는 일정 수정**

사용자는 월별 캘린더에서 결제일, 갱신일, 무료체험 종료일, 혜택 만료일과 일반 일정을 구분해 확인한다. 일정 상세에서 연결된 구독 정보로 이동하거나 일반 일정을 수정한다.

### 7-3. 올블릭 투고 흐름

**공통 `+` → 일반 일정 등록 → 개인용 캘린더 선택 → 일정 정보 입력 → 확인 → 완료**

일반 일정은 구독 일정과 분리해 등록할 수 있으며, 캘린더의 필터를 통해 구독 일정·일상 일정·전체 일정을 선택적으로 조회한다.

### 7-4. 동의 및 중복 추천 정책

- AI가 이미지에서 추출한 구독 정보는 사용자 확인 전까지 임시값으로 처리한다.
- AI 분석 결과에는 서비스명, 결제금액, 결제주기, 다음 결제일 등 추출 항목과 수정 가능한 입력값을 함께 제공한다.
- 사용자가 최종 확인하기 전에는 구독 정보를 확정하거나 목록에 반영하지 않는다.
- 기존 구독과 유사하거나 중복 가능성이 있는 혜택은 추천 정보로만 제공하며, 자동 해지·자동 변경은 수행하지 않는다.
- 혜택 제공처와 실제 이용 서비스가 다른 경우 공식 서비스로 이동할 수 있도록 안내한다.
- 외부 캘린더 불러오기 기능, 내부 캘린더 내보내기 기능 (.ics 파일)
- 실제 구독 해지 대행은 사용자의 별도 동의만으로 범위를 확대하지 않는다.

### 8-2.  📈 장기 성장/비즈니스 지표 (Growth & Business)

#### 1️⃣ [장기 성장 지표-1]  **결제주기 기반 Retention**

 - “사용자가 다음 구독 결제 시점에도 다시 구독을 확인하고 관리했는가?”

> 한 번 서비스를 이용한 사람이 **다음 결제 시점에도 다시 서비스를 이용하는 비율**
> 

| 계산식 | **다음 결제 시점에 다시 이용한 사용자 수 ÷ 다음 결제 시점에 결제할 구독이 있는 사용자 수 × 100** |
| --- | --- |

<aside>

**예시**

- 다음 결제 시점에 결제할 구독이 있는 사용자: 1,000명
- 그중 다시 서비스를 이용한 사용자: 400명
- **Retention = 400 ÷ 1,000 × 100 = 40%**
</aside>

---

**1. 다시 이용한 사용자 기준**

단순히 앱을 켠 것이 아니라, **결제 전에 구독 정보를 확인하거나 구독을 관리한 경우**로 정의

**2. 성장 논리**

- 구독 관리는 결제일에 집중되는 행동이므로, 일반 D7·D30 리텐션으로는 실제 가치 반복을 측정하기 어려움
- 결제 주기마다 돌아오는 사용자가 누적되어야 WAMU가 신규 유입에 의존하지 않고 유지됨

**3. 주의할 점**

> ⚠️ 목표 수치는 베타에서 첫 결제 주기 데이터를 확보한 뒤 기준선을 설정한다
> 
- 월간·연간 등 **구독 기간이 다른 사용자는 구분해서 측정**
- '다음 결제 시점'의 기준 기간을 명확하게 설정
- 앱 방문보다 **실제 구독 확인·관리 행동**을 기준으로 측정
- 사용자 수가 너무 적을 경우 수치가 쉽게 변할 수 있으므로 **전체 사용자 수(N)도 함께 확인**

#### 2️⃣ [장기 성장 지표-2]  **마이데이터를 통한 실질 절감액 (Verified Savings)**

- "틈을 통한 관리 행동이 실제 결제 데이터 기준으로 지출을 줄였는가?"

> 마이데이터 연동을 통해 확인된 실제 결제 내역 기준, 사용자의 관리 행동(해지·일시정지·요금제 변경·중복 해소) **전후 구독 지출 변화량 (카드사/은행 실측 데이터**로 검증되는 지표)
> 

| 개인 단위
계산식 | 실질 절감액 = 관리 행동 전 N개월 평균 월 구독지출 − 관리 행동 후 N개월 평균 월 구독지출 |
| --- | --- |
| 전체 집계
계산식 | 총 실질 절감액 = Σ(개인별 절감액) |
| 보조 산식
절감 실현율 | 절감 실현율 = 실제 절감 확인된 사용자 수 ÷ 관리 완료 기록 사용자 수 × 100 |

<aside>

**예시**

- 관리 행동 전 3개월 평균 월 구독지출: 45,000원
- 관리 행동 후 3개월 평균 월 구독지출: 28,000원
- **실질 절감액 = 45,000 − 28,000 = 17,000원/월**
</aside>

---

1. 왜 이 지표를 보는가?

- ‘행동을 했는가?’만 확인하여 **‘돈을 아꼈는가?’에 대해 알 수 없음**
- ‘틈’의 슬로건 **‘새는 구독비를 잠그다’를 숫자로 직접 증명**하는 지표
- 마이데이터 연동 전에는 **실제 결제 내역을 확인할 수 없음**
→ 사용자의 해지 기록이 실제 결제 중단으로 이어졌는지 검증 불가능
- **관리율은 높은데 절감 실현율이 낮다면**, 앱 기록과 실제 결제가 **어긋나고 있다는 신호**
1) 해지 시도가 실제 해지 완료로 이어지지 않았을 가능성
2) 지출을 줄이지 않는 행동(계속 이용 결정, 현황 조회)이 관리로 집계되었을 가능성

2. 측정 조건 및 전제

| 조건 | 내용 |
| --- | --- |
| **전제** | 마이데이터 연동 완료, 결제 데이터 접근 권한 확보 |
| **측정 대상** | 관리 완료(해지/일시정지/변경/중복해소) 기록 보유 사용자 |
| **관찰 기간** | 전후 최소 1개월, 신뢰도 확보 위해 3개월 권장 |
| **데이터 매칭** | 결제 내역 ↔ 앱 내 등록 구독 매칭 필요 (오류율은 가드레일로 별도 관리) |

3. **주의할 점**

> ⚠️ 마이데이터 연동 자체가 미래 전제이므로 6주 목표에는 포함하지 않으며, 연동 시점부터 기준선을 새로 설정한다
> 

| 이슈 | 내용 | 대응 방향 |
| --- | --- | --- |
| **연간 구독 왜곡** | 연 단위 결제 해지 시 월평균 절감액 과대/과소 산정 가능 | 결제주기 정규화 필요 |
| **해지 후 재구독** | 절감 확인 후 동일/유사 서비스 재구독 시 지표 왜곡 | 재계산 로직 + 역행 감지 가드레일 연결 |
| **인과관계 vs 상관관계** | 절감이 틈 때문인지, 이미 하려던 결정을 틈이 기록만 했는지 불분명 | 관리 행동 전 "확인" 이벤트 선행 여부로 보정 |

#### 3️⃣ [장기 비즈니스 지표]  **6주 내 WAMU 30% 이상 도달**

 - "사용자가 충분한 규모로 계속 유입되고 있는가?”

### 정의

> **WAMU (Weekly Active Meaningful Users) : 주간 의미있는 이용자 수**
일주일 동안 ‘틈’의 핵심 기능을 **1회 이상 끝까지 완료한** 순 사용자 수
(로그인·화면 조회만 한 사용자는 미포함, 완료까지 도달한 경우만 포함)
> 
- 이벤트 기준: `meaningful_use_completed` 발생 1회 이상
- 집계 방식: 중복 제거 (동일 주 반복 이용 시 1명으로 계산)

---

### 비즈니스 목표

> **기준 주 대비 6주 내 WAMU 30% 이상 성장 (53명 → 69명 이상)**
> 

| 항목 | 값 |
| --- | --- |
| 기준 주 WAMU (A) | 53명 |
| 관찰 기간 | 6주 |
| 목표 성장률 | 30% 이상 |
| 목표 WAMU (B) | 69명 이상 |

**산출 근거**

- 가입 목표 150명 (부트캠프 프로젝트 특성상 소규모 베타 
— 지인·커뮤니티 홍보 범위 내 3개월 내 가입 목표)
- 신규 활성화율 35% — 구독 관리 앱은 결제 정보를 다루는 **핀테크 성격**을 겸하므로, 
일반 소비자 앱 활성화율(25~40%)과 핀테크 앱 평균 활성화율(약 44%) 사이 값을 채택
- 기준 WAMU = 150명 × 35% ≈ **53명**
- 관찰 기간 6주 = 구독 결제 주기(월 1회, 약 4주) 1회 경과 + 재방문·재결제 확인용 여유 2주
- 목표 성장률 30% = 유료 마케팅 없이 자연 유입·입소문만으로 달성 가능한 보수적 목표

> ⚠️ 150명 / 35% / 30%는 출시 전 가정값. 베타 운영 데이터 확보 시 재산정 필요
>

    | 관찰창 단축 | 6주 프로젝트 특성 반영, 1~2주 단위로 좁혀 조기신호 확보 |

    ### G1. 단순 확인 사용율
    
    #### **왜 50%인가**
    
    - 이 비율이 절반을 넘으면 "확인→행동" 구조 자체가 무너짐
    - 북극성 지표(확인+행동 동시충족)가 통계적으로 성립하기 어려워지는 임계선
    
    ---
    
    ### G2. 관리행동 후 사용자 재방문율
    
    #### **왜 40%인가**
    
    - 기존 캘린더 미등록/미지속 실패율(약 60%)의 반대 지점
    - 최소한 이 수준은 넘어야 "개선"이라 말할 수 있는 최소선
    
    #### **왜 2주 관찰창인가**
    
    - 6주라는 짧은 프로젝트 기간 내 조기신호 확보 목적
    
    ---
    
    ### G3. 앱 이탈률 (Churn, 2주 연속 미접속 기준)
    
    #### **왜 35%인가**
    
    - 표본 규모 소규모(부트캠프생 모집, n 미정) → 너무 타이트하게 잡으면(10~20%) 몇 명 이탈만으로 "목표 실패" 왜곡 발생
    
    #### **왜 2주 연속 기준인가**
    
    - 4주·6주 연속 기준으로 잡으면 프로젝트 종료 시점까지 신호 자체가 안 나와 가드레일 실효성 상실
    
    ---
    
    ### G4. 신규유입 후 1주 이탈률
    
    #### **왜 50%인가**
    
    - 시장 벤치마크: 일반 앱 D7 리텐션 5~7%(=이탈 93%+), 단 이는 유료 UA 유입 불특정 사용자 기준
    - 틈 테스터는 지인기반 협조적 참여자라 초반 접속 의지 높음 → 시장평균보다 완화
    - 단, 협조적 참여자라도 실사용 니즈 없으면 한 번 켜고 이탈 가능 → 절반 이상 이탈하면 "테스트 협조 자체가 실패"로 보는 임계선

    ## 장기 가드레일 지표 임계값 설정 근거
    
    #### 공통 설계 원칙
    
    | 원칙 | 내용 |
    | --- | --- |
    | **운영 기준선 기반** | 장기 지표는 실제 출시 후 확보한 행동 데이터를 기준선으로 삼음 |
    | **성장지표 왜곡 방지** | Retention과 실질 절감액이 사용자 피로 또는 데이터 오류로 높아지는 현상을 감시 |
    | **지표별 관찰창 적용** | 알림 해제율은 결제주기를 고려해 4~8주, 매칭 오류율은 데이터 연동 이후 지속적으로 관찰 |
    | **초기 기준의 재조정** | 실제 사용자·결제 데이터가 누적되면 기준선과 임계값을 재설정 |
    
    ### G1. 알림 수신 해제율
    
    #### 왜 ‘기준선 대비 증가하지 않도록 유지’인가
    
    - 현재 실제 사용자의 알림 해제 행동 데이터가 없어 특정 절대 수치를 임의로 설정하기 어려움
    - 서비스마다 알림 유형·빈도·사용 목적이 달라 일반적인 시장 평균을 그대로 적용하기 어려움
    - 결제주기 기반 Retention이 상승하더라도 알림 해제율이 함께 상승하면, 핵심가치보다 과도한 알림으로 만들어진 재방문일 가능성이 있음
    - 따라서 출시 후 실제 알림 해제율을 기준선으로 설정하고, 이후 **기준선보다 증가하지 않는 것**을 최소 관리 기준으로 삼음
    
    #### 왜 4~8주 기준선인가
    
    - 월간 구독 사용자가 최소 1회 이상의 결제주기와 결제 전 알림을 경험할 수 있는 기간
    - 1~2주의 짧은 관찰로는 일시적인 알림 해제와 반복적인 알림 피로를 구분하기 어려움
    - 4~8주 동안 알림 유형과 발송 횟수별 해제율을 관찰해야 안정적인 초기 기준선 확보 가능
    
    ### G2. 마이데이터 구독 매칭 오류율
    
    #### 왜 5% 이하인가
    
    - 실질 절감액은 실제 결제내역과 등록 구독이 정확하게 연결되어야 계산할 수 있음
    - 매칭 오류는 실질 절감액을 과대 또는 과소 계산하여 지표의 신뢰도를 직접 훼손함
    - 오류율 5%는 전체 자동 매칭 20건 중 최대 1건의 오류를 허용하는 수준으로, 자동 계산 결과를 제공하기 위한 내부 최소 품질선으로 설정
    - 오류율이 5%를 초과하면 실질 절감액을 자동 확정하기 어렵다고 판단하고, 사용자 확인 또는 운영 검수 범위를 확대해야 함
    
    #### 왜 정확도 95% 이상인가
    
    - 실질 절감액은 금액과 직접 연결되는 정보이므로 일반적인 탐색·추천 정보보다 높은 정확성이 필요함
    - 정확도가 낮으면 실제 절감 여부와 관계없이 성과가 발생한 것처럼 보일 수 있음
    - 따라서 **매칭 정확도 95% 이상**을 실질 절감액 산출을 위한 내부 최소 신뢰 기준으로 설정
    
    #### ⚠️ 기준 해석 시 주의사항
    
    - 95%는 외부 시장 벤치마크가 아니라 초기 운영을 위한 내부 품질 기준
    - 마이데이터 연동 후 실제 매칭 검수 결과에 따라 임계값을 강화하거나 재조정
    - 오류율 5%를 초과하면 자동 계산을 중단하고, 신뢰도가 낮은 항목은 `확인 필요` 상태로 제공
